# Roadmap

## Status (as of 2026-09-02)

All 5 of the original MVP milestone screens were originally built running entirely on local mock data with no backend: Home Dashboard, Training Calendar (with hand-built drag-to-reorder), Workout Detail, AI Coach (scripted replies, no real LLM), and Progress. Onboarding (9 steps) and Profile are built too. As of 2026-09-01, all 5 of the original MVP screens read at least some real Supabase data — Home, Training, and Workout Detail fully; Progress and Coach partially (see below for both: Progress's four honest-placeholder sections, Coach's still-scripted chat replies).

This gives #5 Daily workout page real substance now (Training's week view and Workout Detail both read real `workout` rows, with honest placeholders where the schema genuinely has nothing to show yet). #6 Progress tracking is real for consistency (the one part of it the schema can actually back today) and honestly placeholdered everywhere else — see below for why most of that screen has no real data source at all, not just an unpopulated one. #8 Manual override inputs are real too, in a deliberately thin v1 (report + log only — see below for why). #7 the adaptation audit trail is done end to end: `adaptation_event` has real writers and two real readers now — Workout Detail's HISTORY section (one workout's own events) and Coach's opening transcript (the athlete's recent events across every workout, see below) — both reading the same rows back in plain athlete-facing language. #1 the adaptive scheduling engine now exists too, in a deliberately narrow rule-based v1. #10 safety guardrails also has a first real piece, added the same update: a taper-load guardrail on every reschedule path (manual and engine) — see below for exactly what all three do and don't do, and why each is this narrow. #9 (calendar/wearable integrations, Strava) hasn't been started. Everything in **Now** below still describes real, unstarted work except where marked done — this status note doesn't change the priority order, it just makes clear what "built" actually means so far.

### Backend (added 2026-09-01)

A live Supabase project now backs this app (see [DATABASE.md](DATABASE.md) for the schema as actually built, vs. the target list there). What's real:

- `core_schema` migration: `athlete_profile`, `race`, `training_plan`, `training_phase`, `workout`, `workout_step`, `workout_target_zone`, `workout_completion` — all RLS-scoped to `auth.uid()`.
- `adaptation_audit_schema` migration (added 2026-09-01): `adaptation_event` + `engine_version` — the audit trail behind Workout Detail's "why this changed" section and Progress's future trend data. See [DATABASE.md](DATABASE.md) for the shape and the RLS reasoning (append-only by design, not the schema's usual `for all` pattern). Real writers as of 2026-09-01 (see below): manual overrides, manual reschedules, and now the adaptation engine itself. Real reader as of 2026-09-01: Workout Detail's HISTORY section (see below). `engine_version` has its first real row as of this update — `v1`, seeded by a data migration (`seed_engine_version_v1`) rather than the app, since the table is write-only via migrations/service role by design (see [DATABASE.md](DATABASE.md)).
- `calendar_connection`, `activity_import` are still deferred — no calendar integration or activity-import feature exists yet. `wearable_connection` and `recovery_signal` are real as of 2026-09-02 (see below) — Apple Health is the one live provider; the schema's Garmin/COROS/Strava/Zwift/Google Health Connect `CHECK` values exist for a provider-independent shape (per API.md's own note that this matters strategically, not just as clean code) but have no code behind them yet.
- `lib/supabase/client.ts` — a real client, session persisted via AsyncStorage.
- Onboarding's Account step now calls real Supabase Auth (`signUp`) and, when a session comes back immediately, inserts a real `athlete_profile` row (and a `race` row if a goal/race was set).

**Sign-in + session-gated routing (added 2026-09-01):** `app/index.tsx` now checks `supabase.auth.getSession()` (plus `onAuthStateChange` to stay current) before redirecting — a signed-in athlete lands in `/(tabs)`, everyone else goes to onboarding. Welcome's "I already have an account" link now goes to a new `/sign-in` route (`features/auth/screens/SignInScreen.tsx`, email/password via `signInWithPassword`) instead of doing nothing. Not yet handled: a session that exists but has no matching `athlete_profile` row (e.g. an unconfirmed signup that later got a session some other way) still lands in `/(tabs)` rather than being routed to finish onboarding — there's no real case that hits this today, but it's a gap once onboarding can be abandoned mid-flow with a session already issued.

What's explicitly **not** done, and is a real product decision before going further, not an oversight:

- **Email confirmation.** This project's default Supabase Auth settings likely require it, which means `signUp()` often won't return a session immediately — no session means no `athlete_profile`/`race` row yet (RLS correctly blocks that), and there's nowhere for that athlete to land afterward until they sign in for real (now possible, see above) once confirmed — or until confirmation is turned off in the dashboard. Still not confirmed done on the user's side.
- **Coach's ongoing chat is still scripted** — sending a message still echoes one of three hardcoded `cannedReplies`, since there's no real LLM/AI integration anywhere in this project. That part is unchanged and intentionally out of scope; see below for what did become real. **Home, Training/Workout Detail, (partially) Progress, and (partially) Coach are done (all added 2026-09-01)** — see below.

**Home wired to real data (added 2026-09-01):** `@tanstack/react-query` is now a real dependency (`lib/queryClient.ts`, provider wired in `app/_layout.tsx` — the first real use of the "TanStack Query for server state" line in ARCHITECTURE.md). `features/home/services/fetchHomeDashboard.ts` queries the athlete's active `training_plan` + this week's/upcoming `workout` rows + their next race; `features/home/utils/buildHomeViewModel.ts` (pure, no React) turns that into exactly the display shapes the existing Home components already expected, so the components themselves barely changed. Real states added: a loading spinner, an error state with retry, a "no plan yet" state (any athlete whose distance isn't Sprint/Olympic), and a "Rest day" card (a plan exists but today has nothing scheduled — a legitimate state, not an error). TSS is now optional on `TodayWorkout` and simply omitted from the UI rather than faked — `workout.planned_tss` is null for every generated workout (needs athlete threshold data onboarding doesn't collect, same reasoning as the plan generator's own zone-data gap). Recovery score, coach message, and personal-record line render the honest placeholders decided above. `lib/supabase/useSession.ts` is a new shared session hook (`app/index.tsx` now uses it too instead of its own copy of the same logic). Tapping today's workout or an upcoming one now navigates to the real Workout Detail modal (`HomeScreen.tsx` calls `useRouter()` directly with the real `workout.id` — the old `onOpenWorkout` prop was dead code, since the parent route rendered `<HomeScreen />` with no props at all).

**Training + Workout Detail wired to real data (added 2026-09-01):** `features/training/services/fetchTrainingWeek.ts` queries the athlete's active plan, this calendar week's `workout` rows, and its `training_phase` rows; `features/training/utils/buildTrainingViewModel.ts` turns that into the same 7-row week shape the hand-built drag-reorder list already expected, synthesizing a "Rest Day" placeholder row (`isReal: false`) for any calendar day with no scheduled workout — the plan generator never inserts explicit rest rows. `WorkoutStatus` gained a `'past'` value: `workout.status` in the schema is only ever `planned`/`completed`/`missed`, so a `planned` workout whose date has already elapsed is honestly "untracked," not silently relabeled `'upcoming'` (which would make it draggable) or `'missed'` (which would be a fabricated claim). `tss`/`calories`/`warmup`/`mainset`/`cooldown` are now optional on `PlannedWorkout`, degrading the same way TSS does on Home; Workout Detail shows one honest note in place of the warm-up/main-set/cool-down timeline when none of the three are available, instead of three literal "—" rows (per-user decision, "Honest placeholders, same as Home"). Workout Detail now also queries the real `workout_step`/`workout_target_zone` child tables (`features/training/services/fetchWorkoutDetail.ts`) — nothing writes to them yet, but querying them for real rather than assuming they're always empty means this screen is already correct for whenever something does start writing them.

Drag-to-reorder now persists (per-user decision, "just do what you think is best"): `features/training/hooks/useReorderWorkout.ts` is a TanStack `useMutation` that swaps (or, dropped onto an empty Rest Day, moves) real `workout.scheduled_date` values, optimistic with rollback on failure — simpler than the mock's cascading splice/shift, since a real reorder only ever needs "this workout's date ↔ that workout's date," not a full list re-key. The mock week (`shared/store/useTrainingStore.ts`, `features/training/data/mockTrainingData.ts`) is untouched and still backs Coach's and Progress's own mocks — only `TrainingScreen.tsx` and `WorkoutDetailScreen.tsx` were repointed at real data.

**Progress partially wired to real data (added 2026-09-01):** unlike Home and Training, most of this screen has **no real data source anywhere in the schema at all**, not just an unpopulated one — the fitness/fatigue trend chart is explicitly on this doc's own "Explicitly postponed" list (CTL/ATL/TSB-style dashboards), the VO₂ Max/FTP/threshold-pace/CSS-pace stats need a performance-test table that was never designed, monthly mileage needs a distance field `workout` doesn't have, and personal records need a tracking table that doesn't exist. Consistency is the one exception — it's computable from real `workout.status`/`scheduled_date` values, so `features/progress/services/fetchProgress.ts` computes a real 12-week completion percentage per week, and `ProgressScreen.tsx` renders it through the real `ConsistencyGrid`. Per-user decision (asked directly, given how much of this screen that leaves as placeholder — chose "wire what's real, placeholder the rest"): the other four sections each show one honest "coming soon" note instead of mock numbers, rather than mixing real and fabricated data on the same screen. `ConsistencyGrid` gained a `null` cell state (an empty outlined square) for a week with nothing due yet to measure — showing that as a filled 0% would read as "attempted and missed everything," which isn't what "no data yet" means. `mockProgressData.ts`, `FitnessChart.tsx`, and `MileageChart.tsx` are untouched, ready for whenever a real source exists to feed them.

**Manual override inputs — v1 done (added 2026-09-01), report + log only:** per-user decision (asked directly, since 4 of the 5 override types only make full sense once the adaptation engine — #1, not built — can actually replan around them): every reason is real, but without an engine, the honest v1 outcome is "log it for real, apply the one outcome that's mechanical and unambiguous, let the athlete decide the rest" rather than any real auto-rescheduling. A new `features/overrides` feature adds a "What's going on today?" entry point on Home (`app/report.tsx`, a modal, only shown once a plan exists) listing 4 reasons — illness, travel, poor sleep, extra time (`features/overrides/screens/ReportOverrideScreen.tsx`). Illness/travel/poor-sleep additionally mark today's real workout `missed` if it's still `planned` (`features/overrides/services/reportOverride.ts`) — the one outcome all three share unambiguously. Extra time only logs — there's no engine to decide what to add. Every report writes a real `adaptation_event` row via the new shared `lib/adaptation/logAdaptationEvent.ts`.

The 5th reason, "move this workout," is handled separately since it's inherently about one specific workout and a target date, not a general report: it's now an action on Workout Detail itself, sharing `features/training/hooks/useReorderWorkout.ts` with Training's drag-reorder rather than duplicating the date-change logic — tapping it lists the other days in the workout's own calendar week that are valid drop targets (`canAcceptDrop`, the same rule the drag gesture uses) and runs the same swap-or-move mutation. This also closed a real gap the original drag-reorder had: `useReorderWorkout` now logs a real `adaptation_event` per affected workout for _every_ reschedule, drag-triggered or explicit, not just the ones that go through the overrides screen. Scope limit, documented in code: both "move this workout" and drag-reorder are confined to the current calendar week — Training has no next-week view yet to offer targets beyond it.

**Adaptation audit trail — read side done (added 2026-09-01):** `adaptation_event` has had real writers since manual overrides shipped (above), but nothing read them back until now. `features/training/services/fetchWorkoutHistory.ts` queries the table for rows whose `workout_id` matches the workout being viewed, newest first; `WorkoutDetailScreen.tsx`'s new HISTORY section renders each one's `summary` — already the athlete-facing sentence every writer crafts (e.g. "Reported feeling sick.", `Moved "Tempo Run" to a new date.`) — with a short relative date (`shared/utils/format.ts`'s new `formatEventDate`: "Today"/"Yesterday"/`Jun 15`). No new writer, no new table, no `trigger_type`-to-label mapping needed — the summaries were already written for exactly this. Shown for both rest and non-rest workouts; simply omitted (not placeholdered) when a workout has no history, since that's the normal case for most workouts, not a gap. `reasoning` isn't surfaced in the UI yet, but as of the engine below it's no longer always `null` either.

**Adaptive scheduling engine — v1 shipped, rule-based and deliberately narrow (added 2026-09-01):** per-user decision (asked directly, since this is the first feature that actually _decides_ something rather than reading/writing data as given): v1 is deterministic, no ML, and covers exactly 3 triggers — a missed workout via illness, travel, or poor-recovery report. Calendar-conflict and extra-time stay report-only (as they already were) until calendar integration (#2, not started) gives extra-time something real to act on and a conflict something real to detect.

The rule itself (`lib/adaptation/engine/adaptAfterMissedWorkout.ts`), called right after `reportOverride.ts` marks today's workout `missed`: **don't try to make up the lost session.** Redistributing a missed workout's volume onto other days this week — compressing, doubling up — is exactly the kind of thing that can turn one missed day into overreaching, and this app had no safety guardrails at the time this rule was designed to check that's safe. Instead, the next remaining `planned` workout _this calendar week_ gets its `planned_duration_min` trimmed by ~20% (floored at 15 minutes) — an "ease back in" adjustment that's safe by construction: it only ever removes load, never adds it. Deliberately not discipline- or intensity-aware: `workout.intensity` is free text written by the plan generator's own templates ('Threshold (Z4)', 'Easy (Z1-Z2)', …), not a CHECK-constrained enum — pattern-matching it to classify "hard" vs "easy" would be exactly the fragile, unreliable inference this app avoids elsewhere. Duration is the one signal every generated workout reliably has.

Every engine adjustment writes a real `adaptation_event` with a real `engine_version_id` — the first writer to ever set one — plus real `reasoning` text explaining the trim, on top of the athlete-facing `summary` every writer already provides. `lib/adaptation/engine/getEngineVersionId.ts` looks that id up by the stable `version` string (`'v1'`) rather than hardcoding it, per Supabase's own migration guidance not to hardcode references to generated ids; if the lookup fails (an unmigrated environment), the engine skips adapting anything entirely rather than logging a decision it can't honestly attribute. No new UI was needed to show this — it lands on whichever workout got trimmed, and that workout's own Workout Detail HISTORY section (above) already renders it.

**Safety guardrails — first real piece, taper-load protection (added 2026-09-01):** per-user decision (asked directly, since "load spike" in this item's own original description implies tracking accumulated training stress over time — TSS/CTL/ATL/TSB — which this schema mostly can't compute, the same gap Progress's own honest placeholders already point at): v1 covers **exactly one** of the three things this item originally named, on the one signal that's real today — `planned_duration_min` and `scheduled_date`. `lib/adaptation/guardrails/checkTaperLoadGuardrail.ts`: during a `Taper` phase, no mutation in this app — the v1 engine's own adjustment or a manual reschedule — may increase a calendar day's total planned duration. The engine already can't (it's structurally trim-only, see above), so this guardrail's real effect is on `useReorderWorkout.ts` (both Training's drag-reorder and Workout Detail's "Move this workout"): swapping in a longer session, or moving a real workout onto what was a rest day, is blocked during taper specifically, since adding load there works against the entire point of tapering. A blocked drag silently "snaps back," same UX as any other rejected drop; a blocked "Move this workout" shows an athlete-facing reason instead of looking like nothing happened. Load-spike detection across weeks and injury/illness rest recommendations are still explicitly out of scope — both need real training-load history this schema doesn't have yet.

**Coach — real explanations, last of the 5 MVP screens off mock data (added 2026-09-01):** the screen's opening transcript is no longer the hardcoded "Alex Rivera, recovery 72" mock persona — `features/coach/services/fetchRecentAdaptationEvents.ts` reads the athlete's own recent `adaptation_event` rows (same table and columns as Workout Detail's HISTORY reader, just across every workout instead of one, capped at 15, no pagination yet), and `utils/buildCoachTranscript.ts` turns them into the same "SCHEDULE ADJUSTMENT" recommendation bubbles the design source always had — they're just genuine now. An athlete with no adaptation history yet gets an honest "no changes yet" note instead of a fabricated example. `CoachScreen.tsx` is now split into a data-fetching wrapper (loading/error states, same pattern as Home/Training/Progress) and `CoachChat`, mounted only once the real transcript is in hand so its `useState` seed can't be clobbered by a later background refetch. What's deliberately unchanged: free-text send/reply still echoes a scripted `cannedReplies` line — there's no real AI/LLM anywhere in this project (even the adaptation engine is deterministic rules, not generation), so making the ongoing conversation "real" is a separate, later milestone, not part of this.

**Apple HealthKit read integration — v1 shipped, resting HR + HRV only (added 2026-09-02):** per-user decision (asked directly: build now vs. wait until a dev client exists — chose "write the code now"), this is real integration code, but it can't run yet on the app's current build method — see the caveat below before testing. `wearable_schema` migration adds `wearable_connection` (one row per athlete/provider, `status` connected/disconnected) and `recovery_signal` (one row per athlete/day/source, `resting_hr_bpm` + `hrv_ms`; `sleep_duration_min` exists but is unpopulated — see below), both RLS-scoped to `auth.uid()` the same way every other table is. `lib/wearables/appleHealth/healthKitAdapter.ts` isolates every call into `@kingstinct/react-native-healthkit` (the native module) behind plain typed functions; `lib/wearables/syncAppleHealthRecoverySignals.ts` requests read authorization, pulls the last 7 days of resting HR and HRV, averages same-day samples, and upserts both tables. Onboarding's Wearables step (`features/onboarding/screens/WearablesScreen.tsx`) is the one wired entry point: tapping "Apple Health" now runs a real HealthKit authorization + sync instead of a local-only toggle, and only shows "Connected" on genuine success — a denied/unavailable/failed attempt shows an honest inline error instead. The other 4 rows (Garmin, COROS, Strava, Zwift) are untouched local-only toggles, since none of those integrations exist. Profile's separate "Connected Services" section (still fully mock, including a hardcoded fake `appleHealth: true`) was deliberately left alone this round — wiring only one of its 7 rows to real data would reintroduce the exact "half real, half fake" inconsistency Profile's own code comments already warn against; that's a follow-up task, not an oversight.

**Real caveat, not yet resolved:** HealthKit is a native module — it cannot run in Expo Go (the app's current build/test method). Testing this for real needs a custom dev client (`eas build --profile development` or `expo run:ios`), which in turn needs an Apple Developer account (the HealthKit entitlement generally requires the paid Program) and a physical iOS device (the Simulator has no real HealthKit data). None of that infrastructure exists yet — this code was written and type/lint/format-verified, but has not run against real HealthKit on a device. **Also deliberately deferred, not attempted:** sleep-analysis syncing (`sleep_duration_min` stays null) — HealthKit's sleep data is a category sample with a stage-value enum (inBed/asleepCore/asleepDeep/asleepREM/awake) that would need real mapping logic this session couldn't verify with any confidence; resting HR and HRV are HealthKit's best-documented, most stable quantity samples, which is why v1 is scoped to just those two.

**#20 Signups-over-time view — done (added 2026-09-01).** Per-user decision (asked directly, given the real options — a new authenticated in-app admin screen would be real scope expansion, the app has none today): a SQL view, not new app code. `public.waitlist_signups_by_day` (migration `create_waitlist_signups_by_day_view`) returns one row per calendar day with `signups` and a running `cumulative_signups`, queryable directly in the Supabase SQL editor (including its built-in chart view) any time.
