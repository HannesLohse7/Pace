# Roadmap

## Status (as of 2026-09-02)

All 5 of the original MVP milestone screens were originally built running entirely on local mock data with no backend: Home Dashboard, Training Calendar (with hand-built drag-to-reorder), Workout Detail, AI Coach (scripted replies, no real LLM), and Progress. Onboarding (9 steps) and Profile are built too. As of 2026-09-01, all 5 of the original MVP screens read at least some real Supabase data — Home, Training, and Workout Detail fully; Progress and Coach partially (see below for both: Progress's four honest-placeholder sections, Coach's still-scripted chat replies).

This gives #5 Daily workout page real substance now (Training's week view and Workout Detail both read real `workout` rows, with honest placeholders where the schema genuinely has nothing to show yet). #6 Progress tracking is real for consistency (the one part of it the schema can actually back today) and honestly placeholdered everywhere else — see below for why most of that screen has no real data source at all, not just an unpopulated one. #8 Manual override inputs are real too, in a deliberately thin v1 (report + log only — see below for why). #7 the adaptation audit trail is done end to end: `adaptation_event` has real writers and two real readers now — Workout Detail's HISTORY section (one workout's own events) and Coach's opening transcript (the athlete's recent events across every workout, see below) — both reading the same rows back in plain athlete-facing language. #1 the adaptive scheduling engine now exists too, in a deliberately narrow rule-based v1. #10 safety guardrails also has a first real piece, added the same update: a taper-load guardrail on every reschedule path (manual and engine) — see below for exactly what all three do and don't do, and why each is this narrow. #9 (calendar/wearable integrations, Strava) hasn't been started. Everything in **Now** below still describes real, unstarted work except where marked done — this status note doesn't change the priority order, it just makes clear what "built" actually means so far.

- `adaptation_audit_schema` migration (added 2026-09-01): `adaptation_event` + `engine_version` — the audit trail behind Workout Detail's "why this changed" section and Progress's future trend data. See [DATABASE.md](DATABASE.md) for the shape and the RLS reasoning (append-only by design, not the schema's usual `for all` pattern). Real writers as of 2026-09-01 (see below): manual overrides, manual reschedules, and now the adaptation engine itself. Real reader as of 2026-09-01: Workout Detail's HISTORY section (see below). `engine_version` has its first real row as of this update — `v1`, seeded by a data migration (`seed_engine_version_v1`) rather than the app, since the table is write-only via migrations/service role by design (see [DATABASE.md](DATABASE.md)).

- `lib/supabase/client.ts` — a real client, session persisted via AsyncStorage.
- Onboarding's Account step now calls real Supabase Auth (`signUp`) and, when a session comes back immediately, inserts a real `athlete_profile` row (and a `race` row if a goal/race was set).

**Sign-in + session-gated routing (added 2026-09-01):** `app/index.tsx` now checks `supabase.auth.getSession()` (plus `onAuthStateChange` to stay current) before redirecting — a signed-in athlete lands in `/(tabs)`, everyone else goes to onboarding. Welcome's "I already have an account" link now goes to a new `/sign-in` route (`features/auth/screens/SignInScreen.tsx`, email/password via `signInWithPassword`) instead of doing nothing. Not yet handled: a session that exists but has no matching `athlete_profile` row (e.g. an unconfirmed signup that later got a session some other way) still lands in `/(tabs)` rather than being routed to finish onboarding — there's no real case that hits this today, but it's a gap once onboarding can be abandoned mid-flow with a session already issued.

What's explicitly **not** done, and is a real product decision before going further, not an oversight:

- **Email confirmation.** This project's default Supabase Auth settings likely require it, which means `signUp()` often won't return a session immediately — no session means no `athlete_profile`/`race` row yet (RLS correctly blocks that), and there's nowhere for that athlete to land afterward until they sign in for real (now possible, see above) once confirmed — or until confirmation is turned off in the dashboard. Still not confirmed done on the user's side.
- **Coach's ongoing chat is still scripted** — sending a message still echoes one of three hardcoded `cannedReplies`, since there's no real LLM/AI integration anywhere in this project. That part is unchanged and intentionally out of scope; see below for what did become real. **Home, Training/Workout Detail, (partially) Progress, and (partially) Coach are done (all added 2026-09-01)** — see below.

**Manual override inputs — v1 done (added 2026-09-01), report + log only:** per-user decision (asked directly, since 4 of the 5 override types only make full sense once the adaptation engine — #1, not built — can actually replan around them): every reason is real, but without an engine, the honest v1 outcome is "log it for real, apply the one outcome that's mechanical and unambiguous, let the athlete decide the rest" rather than any real auto-rescheduling. A new `features/overrides` feature adds a "What's going on today?" entry point on Home (`app/report.tsx`, a modal, only shown once a plan exists) listing 4 reasons — illness, travel, poor sleep, extra time (`features/overrides/screens/ReportOverrideScreen.tsx`). Illness/travel/poor-sleep additionally mark today's real workout `missed` if it's still `planned` (`features/overrides/services/reportOverride.ts`) — the one outcome all three share unambiguously. The 5th reason, "move this workout," is handled separately since it's inherently about one specific workout and a target date, not a general report: it's now an action on Workout Detail itself, sharing `features/training/hooks/useReorderWorkout.ts` with Training's drag-reorder rather than duplicating the date-change logic — tapping it lists the other days in the workout's own calendar week that are valid drop targets (`canAcceptDrop`, the same rule the drag gesture uses) and runs the same swap-or-move mutation. **Adaptation audit trail — read side done (added 2026-09-01):** `adaptation_event` has had real writers since manual overrides shipped (above), but nothing read them back until now. `features/training/services/fetchWorkoutHistory.ts` queries the table for rows whose `workout_id` matches the workout being viewed, newest first; `WorkoutDetailScreen.tsx`'s new HISTORY section renders each one's `summary` — already the athlete-facing sentence every writer crafts (e.g. "Reported feeling sick.", `Moved "Tempo Run" to a new date.`) — with a short relative date (`shared/utils/format.ts`'s new `formatEventDate`: "Today"/"Yesterday"/`Jun 15`). No new writer, no new table, no `trigger_type`-to-label mapping needed — the summaries were already written for exactly this. Shown for both rest and non-rest workouts; simply omitted (not placeholdered) when a workout has no history, since that's the normal case for most workouts, not a gap. `reasoning` isn't surfaced in the UI yet, but as of the engine below it's no longer always `null` either.

**Adaptive scheduling engine — v1 shipped, rule-based and deliberately narrow (added 2026-09-01):** per-user decision (asked directly, since this is the first feature that actually _decides_ something rather than reading/writing data as given): v1 is deterministic, no ML, and covers exactly 3 triggers — a missed workout via illness, travel, or poor-recovery report. Calendar-conflict and extra-time stay report-only (as they already were) until calendar integration (#2, not started) gives extra-time something real to act on and a conflict something real to detect.

The rule itself (`lib/adaptation/engine/adaptAfterMissedWorkout.ts`), called right after `reportOverride.ts` marks today's workout `missed`: **don't try to make up the lost session.** Redistributing a missed workout's volume onto other days this week — compressing, doubling up — is exactly the kind of thing that can turn one missed day into overreaching, and this app had no safety guardrails at the time this rule was designed to check that's safe. Instead, the next remaining `planned` workout _this calendar week_ gets its `planned_duration_min` trimmed by ~20% (floored at 15 minutes) — an "ease back in" adjustment that's safe by construction: it only ever removes load, never adds it. Deliberately not discipline- or intensity-aware: `workout.intensity` is free text written by the plan generator's own templates ('Threshold (Z4)', 'Easy (Z1-Z2)', …), not a CHECK-constrained enum — pattern-matching it to classify "hard" vs "easy" would be exactly the fragile, unreliable inference this app avoids elsewhere. Duration is the one signal every generated workout reliably has.

Every engine adjustment writes a real `adaptation_event` with a real `engine_version_id` — the first writer to ever set one — plus real `reasoning` text explaining the trim, on top of the athlete-facing `summary` every writer already provides. `lib/adaptation/engine/getEngineVersionId.ts` looks that id up by the stable `version` string (`'v1'`) rather than hardcoding it, per Supabase's own migration guidance not to hardcode references to generated ids; if the lookup fails (an unmigrated environment), the engine skips adapting anything entirely rather than logging a decision it can't honestly attribute. No new UI was needed to show this — it lands on whichever workout got trimmed, and that workout's own Workout Detail HISTORY section (above) already renders it.

**Safety guardrails — first real piece, taper-load protection (added 2026-09-01):** per-user decision (asked directly, since "load spike" in this item's own original description implies tracking accumulated training stress over time — TSS/CTL/ATL/TSB — which this schema mostly can't compute, the same gap Progress's own honest placeholders already point at): v1 covers **exactly one** of the three things this item originally named, on the one signal that's real today — `planned_duration_min` and `scheduled_date`. `lib/adaptation/guardrails/checkTaperLoadGuardrail.ts`: during a `Taper` phase, no mutation in this app — the v1 engine's own adjustment or a manual reschedule — may increase a calendar day's total planned duration. The engine already can't (it's structurally trim-only, see above), so this guardrail's real effect is on `useReorderWorkout.ts` (both Training's drag-reorder and Workout Detail's "Move this workout"): swapping in a longer session, or moving a real workout onto what was a rest day, is blocked during taper specifically, since adding load there works against the entire point of tapering. A blocked drag silently "snaps back," same UX as any other rejected drop; a blocked "Move this workout" shows an athlete-facing reason instead of looking like nothing happened. Load-spike detection across weeks and injury/illness rest recommendations are still explicitly out of scope — both need real training-load history this schema doesn't have yet.

**Coach — real explanations, last of the 5 MVP screens off mock data (added 2026-09-01):** the screen's opening transcript is no longer the hardcoded "Alex Rivera, recovery 72" mock persona — `features/coach/services/fetchRecentAdaptationEvents.ts` reads the athlete's own recent `adaptation_event` rows (same table and columns as Workout Detail's HISTORY reader, just across every workout instead of one, capped at 15, no pagination yet), and `utils/buildCoachTranscript.ts` turns them into the same "SCHEDULE ADJUSTMENT" recommendation bubbles the design source always had — they're just genuine now. An athlete with no adaptation history yet gets an honest "no changes yet" note instead of a fabricated example. `CoachScreen.tsx` is now split into a data-fetching wrapper (loading/error states, same pattern as Home/Training/Progress) and `CoachChat`, mounted only once the real transcript is in hand so its `useState` seed can't be clobbered by a later background refetch. What's deliberately unchanged: free-text send/reply still echoes a scripted `cannedReplies` line — there's no real AI/LLM anywhere in this project (even the adaptation engine is deterministic rules, not generation), so making the ongoing conversation "real" is a separate, later milestone, not part of this.

**Google Calendar read integration — v1 shipped, freebusy conflict-checking only, backend verified live (added 2026-09-02):** per-user decision (asked directly what to build after HealthKit — Google Calendar, Apple EventKit, or the dev-client work itself; **Google Calendar picked**, specifically because unlike EventKit it doesn't need a native module, so it's the one integration actually testable today without a dev client — see the architecture note below for why that reasoning needed a real correction mid-build).

**Architecture, and why it's not the standard mobile OAuth flow:** the textbook approach (`expo-auth-session`, redirect straight back into the app via a custom URL scheme) turned out to hit the _exact same_ Expo Go limitation as HealthKit — Expo's own docs say Expo Go can't register a custom scheme, and their old workaround for that (the `auth.expo.io` proxy) is now flagged as an actual security risk, not just deprecated. The fix, worked out mid-build rather than assumed upfront: route the whole OAuth exchange through a Supabase Edge Function instead. The consent screen opens in a plain system browser (`expo-web-browser`, which _is_ Expo Go-compatible — only the redirect-back step was the problem); Google redirects to a plain HTTPS callback URL with no custom scheme involved at all; the Edge Function exchanges the code for tokens server-side and stores them; the app polls the real connection row until it lands. This is also just the more secure design regardless of Expo Go — the OAuth client secret and the athlete's refresh token never touch the phone.

**Schema** (`calendar_schema` migration, live, zero unexpected security lints — see docs/DATABASE.md for the one deliberate `rls_enabled_no_policy` INFO lint): `calendar_connection` (athlete-readable, service-role-writable only), `calendar_connection_request` (a short-lived, single-use correlation row the athlete's own client creates right before opening the consent screen, so the unauthenticated callback can recover which athlete a Google redirect belongs to), `calendar_oauth_token` (the actual tokens — zero RLS policies at all, not even for the token's own athlete; only Edge Functions running as service role ever touch it, stricter than every other table in this schema on purpose, since a leaked refresh token here is a real credential against the athlete's actual Google account).

**Three Edge Functions, all deployed and live**: `google-calendar-oauth-callback` (public, `verify_jwt` disabled — implements its own single-use/short-expiry auth via the connection-request row instead, since an OAuth redirect from Google can't carry a Supabase JWT; **verified live** by hitting its real error paths — both the "declined consent" and "expired/invalid link" branches were confirmed against the deployed function, not just read as code), `google-calendar-freebusy` (authenticated, the one real capability: checks busy/free blocks for a time window, refreshing the stored access token first if needed), `google-calendar-disconnect` (authenticated, genuinely revokes the grant with Google — not just a local status flip, unlike HealthKit's permissions, which can only be revoked from iOS Settings).

**Scope, deliberately narrow, and why:** v1 requests only the `calendar.freebusy` scope — Google's narrowest Calendar scope, and notably classified **non-sensitive**, meaning this doesn't need to go through Google's OAuth app-verification review at all. Full event read/write (`calendar.readonly`/`calendar.events`) are both "sensitive" and would need that review — a real, concrete reason (not just caution) to defer write-back (the original item's "Pace workout write-back, never overwrite existing events" half) to a later round. The onboarding Calendar screen's own existing copy — "Pace reads your busy blocks — never event details" — already matched this scope exactly, which is a good sign the narrowing lines up with the original design intent, not just this round's convenience.

**What's wired, and what isn't yet:** onboarding's Calendar step (`features/onboarding/screens/CalendarScreen.tsx`) — its Google Calendar row now runs the real connect/disconnect flow; Apple Calendar remains a local-only toggle (EventKit, same untested-native-module reasoning as Apple Calendar getting deferred behind HealthKit). One honest copy fix made in the same screen: the footer used to claim "Your calendar data stays on-device and is never shared with third parties" — no longer true once real tokens route through Supabase, so it's now "Pace only ever checks whether a time is free or busy — never event titles, locations, or guests," which is what's actually true. **No UI reads `google-calendar-freebusy` yet** — surfacing an actual conflict on Training or Workout Detail is a real UI/UX decision (where, and how, to show it) that wasn't folded into this round; the backend for it is real and working, just not called from anywhere in the app yet.

**Found and fixed (later the same day, 2026-09-02): onboarding's Calendar step can never actually connect, by construction — not a config bug.** While setting up real credentials, a live-device debugging session traced "Couldn't connect — try again" through a `.env` misconfiguration first (wrong Supabase project ref — the user's `.env` pointed at a different project than the one this whole integration was built and migrated against; fixed by the user directly, cross-checked against `mcp__Supabase__list_projects` to confirm which project is real). With `.env` corrected, the same error persisted, and `auth.users`/`athlete_profile` were both still completely empty on the real project. Root cause: `supabase.auth.signUp()` only ever fires on the _last_ onboarding screen, Generating (`features/onboarding/screens/GeneratingScreen.tsx`) — after Wearables, i.e. after Calendar. Onboarding's own Calendar step, where the Google Calendar Connect button lives, is reached _before_ any account exists, so `useSession()` always returns no session there and the connect mutation throws `'No signed-in athlete.'` immediately — before ever opening a browser. This was a gap in how the OAuth flow was wired into the existing (pre-existing) onboarding step order, not an environment issue; no amount of `.env`/credential fixing could have resolved it.

**Fix:** Google Calendar's Connect/Disconnect row is now also wired into Profile's existing "Connected Services" section (`features/profile/screens/ProfileScreen.tsx`) — reusing the same `useConnectGoogleCalendar`/`useDisconnectGoogleCalendar` hooks onboarding already used, gated on the same real `useSession()`. Profile is only reachable once an athlete is actually signed in, so this is now the one place the flow can genuinely be exercised, and the sensible permanent home for reconnect/disconnect regardless (an athlete revoking access from Google's side, say). Onboarding's Calendar step is unchanged — still real, still shown during onboarding — it just can't complete a connection from there until an account exists, same as before. `tsc`/`eslint`/`prettier` all verified clean against the real repo mirror. **Still not verified:** an actual end-to-end round-trip against Google's real consent screen on the user's device — that needs the two Edge Function secrets (`GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET`) confirmed set in the Supabase Dashboard, which hasn't been confirmed done yet, plus a real signed-in athlete (sign up or sign in for real, then open Profile).

**Found and fixed (same day, third layer): a real RLS/PostgREST bug in `createCalendarConnectionRequest`, present since this feature first shipped.** With the Profile-screen fix above, the user now had everything needed (real session, real `athlete_profile` row, confirmed via `execute_sql`) — but Connect still failed, now with "Waiting for Google…" briefly before "Couldn't connect — try again," and `calendar_connection_request` stayed completely empty in the database no matter how many times it was tried. Root cause: `features/calendar/services/calendarConnectionRequest.ts` inserted the correlation row with `.insert({...}).select('id').single()` — but `calendar_connection_request` deliberately has **no SELECT policy at all** (see docs/DATABASE.md; only INSERT is granted, by design, since nothing client-side should ever need to read this row back). PostgREST's RETURNING clause is itself subject to RLS, so with no SELECT policy the insert's own RETURNING output is empty for that role; `.single()` then sees 0 rows where it expected exactly 1, treats that as an error, and PostgREST **rolls back the entire insert** — so the row never actually persisted, the function always threw, and Connect could never have succeeded for _any_ athlete, in _any_ environment, since the day this shipped. Every earlier layer of this debugging session (the `.env` project mismatch, the empty `auth.users`, the onboarding step-order gap) was real and needed fixing, but none of them were the last blocker — this was.

**Fix:** generate the row's id client-side with `Crypto.randomUUID()` (new dependency, `expo-crypto` — official Expo module, Expo Go-compatible, no config plugin needed, same due-diligence as `expo-web-browser`'s addition above) and insert `{id, athlete_id}` with no `.select()` at all — a plain insert needs only the INSERT policy this table already grants, nothing to read back. Verified against the real installed `expo-crypto@15.0.9` package (matched to Expo SDK 54's bundled version) — `tsc`/`eslint`/`prettier` all clean. **Still not verified:** the real end-to-end round-trip against Google's consent screen — same two prerequisites as above (Edge Function secrets confirmed set, a real signed-in athlete), plus now `npm install` on the user's machine to pick up `expo-crypto`.

**Confirmed working end-to-end on a real device (2026-09-02).** Every layer above got a real round-trip: `.env` corrected, a real athlete session, the RLS fix, Google's own consent screen (after fixing a separate Google Cloud Console gap — the OAuth client was stuck in "Testing" publishing status with no branding configured, which 403'd anyone not added as a test user; fixed by completing Branding — logo, authorized domain — and publishing to Production, which non-sensitive-scope apps can do without Google's verification review) — and a real `calendar_connection`/`calendar_oauth_token` row landed, confirmed directly via `execute_sql`. One more real bug turned up at the very end: the "Connected" confirmation page rendered as raw HTML source instead of a real page, because this project's Supabase gateway coerces every non-JSON Edge Function response to `text/plain` (the same reason the waitlist page lives on GitHub Pages, not Supabase). Fixed the same way: `google-calendar-oauth-callback` now redirects (302, no body to mangle) to a new static page, `calendar-connected.html`, deployed to the same GitHub Pages site — see that function's own doc comment for the full story. This was the last blocker; the feature is genuinely done.

**Conflict surfacing — v1 shipped, Workout Detail only, day-level not time-level (added 2026-09-02).** The freebusy backend has existed since Google Calendar connect shipped, but nothing called it until now. `features/calendar/hooks/useWorkoutDayCalendarBusy.ts` checks whether the athlete's connected calendar has anything on a workout's `scheduled_date`, and `WorkoutDetailScreen.tsx` shows a quiet one-line note ("3 events on your calendar today.") when it does — nothing when the day's clear, nothing at all for an athlete with no connected calendar (this never nudges anyone to connect; that's Profile's job).

Deliberately **day-level, not a true time-of-day conflict check** — this is scoped down from what the original item ("Pace workout write-back, never overwrite existing events," API.md) implied, for a real schema reason, not a shortcut: `workout.scheduled_date` is a bare date, with no time-of-day field anywhere in this schema. There's no workout start/end to compare a calendar event's start/end against, so "this exact slot is free" isn't a claim this app can honestly make — only "something's on your calendar that day" is. A real time-level check would need workouts to carry a scheduled time (onboarding's `preferredTimeOfDay` — morning/midday/evening — is collected but never assigned to individual workouts today, and even a time-of-day bucket like "morning" isn't a precise start/end to check against). Worth revisiting once/if workouts get real scheduled times; not attempted here since that's a plan-generator change, not a calendar one.

**Training's week view deliberately not extended the same way** — a per-day badge across 7 rows would mean 7 separate freebusy calls every time the week view opens (real Google API quota cost, shared across every athlete using this feature), and a per-day badge is a different, smaller UI than Workout Detail's one-line note — its own design decision, not folded into this round. `useGoogleCalendarConnectionStatus.ts` is new too — extracted from `useConnectGoogleCalendar`'s own status query (behavior unchanged there) so both the connect flow and this new conflict check share one cache entry instead of each polling/fetching independently.

**Apple HealthKit read integration — v1 shipped, resting HR + HRV only (added 2026-09-02):** per-user decision (asked directly: build now vs. wait until a dev client exists — chose "write the code now"), this is real integration code, but it can't run yet on the app's current build method — see the caveat below before testing. `wearable_schema` migration adds `wearable_connection` (one row per athlete/provider, `status` connected/disconnected) and `recovery_signal` (one row per athlete/day/source, `resting_hr_bpm` + `hrv_ms`; `sleep_duration_min` exists but is unpopulated — see below), both RLS-scoped to `auth.uid()` the same way every other table is. `lib/wearables/appleHealth/healthKitAdapter.ts` isolates every call into `@kingstinct/react-native-healthkit` (the native module) behind plain typed functions; `lib/wearables/syncAppleHealthRecoverySignals.ts` requests read authorization, pulls the last 7 days of resting HR and HRV, averages same-day samples, and upserts both tables. Onboarding's Wearables step (`features/onboarding/screens/WearablesScreen.tsx`) is the one wired entry point: tapping "Apple Health" now runs a real HealthKit authorization + sync instead of a local-only toggle, and only shows "Connected" on genuine success — a denied/unavailable/failed attempt shows an honest inline error instead. The other 4 rows (Garmin, COROS, Strava, Zwift) are untouched local-only toggles, since none of those integrations exist. Profile's separate "Connected Services" section (still mostly mock, including a hardcoded fake `appleHealth: true`) was deliberately left alone this round — wiring only one of its 7 rows to real data would reintroduce the exact "half real, half fake" inconsistency Profile's own code comments already warn against; that's a follow-up task, not an oversight. (Google Calendar's row specifically was wired for real later the same day — see the Google Calendar section above — once it had a real backend behind it and a concrete reason to be there; the other 6 rows are still exactly the mock described here.)

**Real caveat, not yet resolved:** HealthKit is a native module — it cannot run in Expo Go (the app's current build/test method). Testing this for real needs a custom dev client (`eas build --profile development` or `expo run:ios`), which in turn needs an Apple Developer account (the HealthKit entitlement generally requires the paid Program) and a physical iOS device (the Simulator has no real HealthKit data). None of that infrastructure exists yet — this code was written and type/lint/format-verified, but has not run against real HealthKit on a device. **Also deliberately deferred, not attempted:** sleep-analysis syncing (`sleep_duration_min` stays null) — HealthKit's sleep data is a category sample with a stage-value enum (inBed/asleepCore/asleepDeep/asleepREM/awake) that would need real mapping logic this session couldn't verify with any confidence; resting HR and HRV are HealthKit's best-documented, most stable quantity samples, which is why v1 is scoped to just those two.

### Design/UX polish pass — round 1 (added 2026-09-02)

Per-user decision (2026-09-02): while the user was away, work through calendar conflicts → design/UX polish → docs cleanup → marketing drafts, in that order, without further check-ins. This is the design/UX round: a genuine audit of Home, Training, Progress, Coach, and Profile against the approved design direction (Apple Fitness/Whoop/Strava/Garmin/TrainingPeaks, no generic-AI-dashboard patterns), fixing what was safe and self-contained to fix without a real device to test on, and leaving the rest as a punch list rather than guessing. Four fixes shipped:

- **Home's greeting was hardcoded "Good morning" regardless of the actual time of day.** The one line of copy on the app's very first screen was wrong most of the day. `shared/utils/format.ts` gained `formatGreeting(date)` (morning/afternoon/evening, boundaries at 5am/12pm/5pm — the common fitness-app convention, not anything from the design source, since there was no time-aware version to match); `buildHomeViewModel.ts` exposes it as `greeting`; `HomeScreen.tsx` reads it instead of the literal string.
- **Pull-to-refresh was missing everywhere.** Home, Training, and Progress each fetch through a plain `useQuery` and only offered a "Try again" link on hard failure — there was no way to manually refresh on the happy path (after logging a workout elsewhere, after an adaptation event fires server-side) short of force-quitting. `shared/components/Screen.tsx` gained optional `refreshing`/`onRefresh` props (rendered as a `RefreshControl` on the ScrollView, tinted with the accent color, only when `onRefresh` is passed) — Home, Training, and Progress now pass their query's own `isFetching`/`refetch` straight through. Coach deliberately did not get this: its scrolling view is the chat log, and re-fetching the seed transcript after `CoachChat` has already mounted (and the athlete may have typed messages) wouldn't do anything meaningful — see that screen's own doc comment on why the seed is read once via `useState`'s initializer. **Needs a real-device check before calling it done**, specifically on Training: its rows carry a `Gesture.Pan()` drag-to-reorder (long-press-activated, scoped to a small handle icon — see `TrainingWorkoutRow.tsx`) layered over the same ScrollView that now also carries `RefreshControl`. The two gestures look orthogonal on paper (one needs a long press on a specific icon, the other a plain drag from scroll position zero) and this is a common combination in RN apps, but Training's drag-reorder has already gone through three real-device-bug-driven rewrites this project (see that file's own doc comment) — that history is reason enough to flag it rather than assume it's fine.
- **Profile's "Sign Out" was a dead tap target.** It was written inert back when there was no real auth/session concept in the app at all — that stopped being true the moment Google Calendar got a real `useSession()`-backed connect flow (2026-09-02, same day), and an inert Sign Out on a screen with a real signed-in session is no longer an honest placeholder, it's just broken. Now calls `supabase.auth.signOut()` then `router.replace('/')` — the explicit redirect matters because nothing else re-checks session state once mounted (`(tabs)/_layout.tsx` has no session guard; only root `app/index.tsx` does), so without it the athlete would land back on a signed-out Profile screen still sitting inside the tab navigator instead of onboarding. **Also not yet verified on a real device** — should be checked as part of the same pass as the pull-to-refresh items above.
- Everything else audited — Home's card/section structure, Training's phase card and row layout, Progress's placeholder sections, Coach's chat bubbles, Profile's settings rows — held up well against the Apple Fitness/Whoop/Strava reference bar already: real token usage throughout (no ad-hoc hex colors found), no gradients, no generic dashboard-card sprawl, honest "coming soon" states instead of fabricated numbers. Nothing else rose to the level of a fix worth making blind (without a device) rather than flagging.

**Follow-ups, not done this round:**
- Training/Progress/Coach's screen-title text (`text-[26px] font-bold tracking-[-0.5px] text-color-primary`) is copy-pasted identically across all three files rather than a shared component — purely a DRY/consistency issue, zero visual impact, low risk, just didn't make the cut this round.
- Profile's `INITIAL_CONNECTED_SERVICES` mock and the Notifications toggle are unchanged — still deliberately mock, per that screen's own existing doc comments, not part of this pass.
- The two device-unverified items above (Training pull-to-refresh + drag-reorder interaction, Profile sign-out redirect) should be the first thing checked on a real device.
